# Операторууд

[English](operators.md) · **Монгол**

Монголын оператор бүрийн гарцаар SMS илгээхийн өмнө юу шаардагддаг, мөн гарц бүр хүсэлт,
хариуны түвшинд яг хэрхэн ажилладаг тухай.

Дөрвөн гарцыг бүгдийг хамарсан. Операторын өөрийнх нь зааварт байгаа зүйлийг тэгж
тэмдэглэсэн; баримтжаагүй эсвэл хараахан баталгаажаагүй зүйлийг мөн адил ил хэлсэн.
Операторуудын зааврыг энд дахин тараагаагүй — та бүртгэлээ авахдаа хамт нь хүлээн авна.

## Бүх операторт адил зүйлс

**Оператор бүрт өөрийн бүртгэлтэй байх шаардлагатай.** Энэ сангийн ард ямар ч зуучлагч
байхгүй. Оператор бүр бүртгэлтэй байгууллагад "тусгай дугаар"-ын (premium буюу богино
дугаар гэж бас нэрлэдэг) үйлчилгээ худалддаг бөгөөд API нь түүнтэй хамт ирдэг.

**Илгээгч нь таны богино дугаар бөгөөд бүртгэлд бэхлэгдсэн байдаг.** Мессеж бүрт өөрөөр
сонгох боломжгүй. Скайтел өөр утгыг шууд буцаана (`ERROR: 207`); Жи-Мобайл `error2` гэж
хариулна.

**Баталгаажуулалтад хүсэлт илгээсэн IP хаяг ордог.** Гарц бүр хүсэлтийн эх хаягийг таны
бүртгэлд бүртгэсэн жагсаалттай тулгаж шалгадаг. Бүртгэлгүй IP хаягаас ирсэн хүсэлтийг
нэвтрэх мэдээлэл зөв байсан ч буцаана:

| Оператор | Бүртгэлгүй IP хаягт өгөх хариу | Жагсаалтыг хэрхэн удирдах |
| --- | --- | --- |
| Юнител | татгалзана | өөрөө, порталаас: Settings → API key → Hosts |
| Скайтел | `ERROR: 202 not authenticated` | өөрөө, порталаас: Change configurations → Allowed IP List |
| Мобиком | татгалзана | Мобиком бүртгэнэ, хүсэлтээр |
| Жи-Мобайл | `error3` | Жи-Мобайл бүртгэнэ, хүсэлтээр |

Тиймээс танд **тогтмол гадаад IP хаяг** хэрэгтэй бөгөөд түүнийгээ дөрвөн удаа бүртгүүлнэ.
Үүнийг эвддэг зүйлс: serverless функц, түр зуурын хаягтай автоматаар өргөждөг node,
pod нь аль node дээр буусан тэрүүгээрээ гардаг Kubernetes кластер, хөгжүүлэгчийн
компьютер. Урд нь NAT gateway эсвэл тогтмол forward proxy тавьж, тэр хаягаа бүртгүүлээрэй.
Клиентийн `fetch` тохиргоо зарим талаар үүнд зориулагдсан.

**Гарц бүр зөвхөн өөрийн сүлжээ рүү хүргэнэ.** Скайтелийн зааварт үүнийг бичсэн байдаг —
`dest` нь "зөвхөн Скайтелийн дугаар байх ёстой" — бөгөөд `ERROR: 206`-аар хэрэгжүүлдэг.
Бусад гурван операторын зааварт энэ дүрмийг дурдаагүй тул оператор өөрөөр хэлээгүй л бол
тэдэнд ч мөн адил гэж тооцоорой. Буруу оператор руу илгээсэн мессежийг удааширсан биш,
алдагдсан гэж үзнэ. Энэ сан дугаараар чиглүүлдгийн гол шалтгаан энэ.

**HTTP статус бол эцсийн хариу биш.** Скайтел, Мобиком, Жи-Мобайл нь энгийн текстээр
хариулдаг гарцууд бөгөөд мессежийг хүлээн авсан ч, татгалзсан ч `200 OK` буцаадаг. Гол нь
хариуны бие. Зөвхөн `response.ok`-ийг шалгадаг клиент татгалзсан илгээлт бүрийг хүргэгдсэн
гэж бүртгэнэ. Энэ сан гарц бүрийн хүлээн авсан хариуны мөрийг яг тааруулж шалгаад, *бусад
бүх зүйлийг* — баримтжсан алдаа, proxy-ийн HTML хуудас, хоосон хариу — татгалзсан гэж үзнэ.

**Хүлээн авсан гэдэг нь хүргэсэн гэсэн үг биш.** Эдгээр илгээх API-ийн аль нь ч мессежийн
дугаар буцаадаггүй, хүргэлтийн тайлан ч илгээдэггүй. "Accepted" гэдэг нь гарц мессежийг
авсан гэсэн үг. Утсан дээр юу болсныг зөвхөн операторын вэб порталаас харна.

**Дугаар 8 оронтой.** Гарцууд `976`-гүй, цэвэр хэрэглэгчийн дугаар авдаг.

## Бүртгэл авах

Үйл явц оператор бүрт өөр бөгөөд цаг хугацааны явцад өөрчлөгддөг тул операторын
байгууллагын борлуулалтын албанаас лавлаарай. Ерөнхийдөө дараах зүйлсийг хүлээх хэрэгтэй:

1. Таны бүртгэлтэй байгууллага болон операторын хооронд үйлчилгээний гэрээ.
2. Танд оноосон илгээгчийн богино дугаар. Хэд хэдэн оператороос *ижил* богино дугаар авах
   нь элбэг — гэхдээ баталгаатай биш — бөгөөд ингэвэл нэг илгээгч хаа сайгүй ажиллана.
3. API-ийн нэвтрэх мэдээлэл болон гарцын хаягийг агуулсан бүртгэлийн захидал эсвэл
   порталын нэвтрэх эрх.
4. Серверийн IP хаягуудаа бүртгүүлэх (дээр үзнэ үү).
5. Илгээсэн мессежийн төлбөрийг сар бүр нэхэмжилнэ. Жишээлбэл Юнителийн зааварт өмнөх
   сарын нэхэмжлэх дараа сарын 7-нд үүсэж, 21-нээс өмнө төлөх ёстой, төлөөгүй бол дугаарын
   үйлчилгээг түр хаана гэж бий.

Үүнд цаг гаргаарай. Холболт хийх нь хагас өдрийн ажил; бичиг баримт нь тийм биш.

## Юнител

Портал: `https://pn.unitel.mn`. Эх сурвалж: Юнителийн PN хэрэглэгчийн заавар.

**Юу хэрэгтэй вэ**

- Байгууллагынхаа порталын нэвтрэх эрх.
- **Settings → API key** цэснээс үүсгэсэн API key. Үүсгэхдээ:
  - **Premium number** — энэ key аль тусгай дугаараас илгээхийг сонгоно.
  - **Hosts** — серверийн IP хаягууд. Үүнийг оруулаагүй бол таны хаягаас мессеж илгээх
    боломжгүй гэж зааварт тодорхой бичсэн.
  - **Password** — нэг удаа оруулах бөгөөд дахин харагдахгүй. Үүссэн key ч мөн адил.
    Хоёуланг нь хадгалж аваарай.
  - **Regexes** — заавал биш; порталын бүртгэлд мессежийн зарим хэсгийг нууцална.
- Хүсвэл дугаарын оронд илгээгчийн *нэр* ашиглаж болно: **Settings → Premium Number → Name**
  (11 тэмдэгтээс хэтрэхгүй), **Uses name**-ийг идэвхжүүлнэ. Хүлээн авагчид нэр харагдана.

**Тохиргоо**

```ts
unitel: { apiKey: "…" }   // baseUrl-ийн анхны утга: https://pn.unitel.mn
```

**Хүсэлт**

```
POST https://pn.unitel.mn/api/message/send/sms?enc=<API_KEY>
content-type: application/json

{"to":"88112233","message":"…"}
```

Зааварт query string хэлбэр ч бий (`/api/message/send/sms/q?enc=…&to=…&message=…`, GET
эсвэл POST). Кирилл текст JSON биед гэмтэлгүй дамждаг тул энэ сан JSON хувилбарыг ашигладаг.

**Хариу.** Хариуны бие зааварт **баримтжаагүй**. Тиймээс энэ сан HTTP статусаар
шийддэг — 2xx бол хүлээн авсан, бусад нь `rejected` бөгөөд статус нь `gatewayCode` болно —
мөн хариуны биеийг `result.response`-д яг байгаагаар нь буцаана (JSON бол задалсан
хэлбэрээр). Үүнийг логт бичээрэй; асуудал гарахад таны цорын ганц нотолгоо.

**Хязгаар.** Мессежийн уртын хязгаар баримтжаагүй тул энд шалгахгүй.

**Хариу мессеж хүлээн авах.** Юнител хэрэглэгчийн хариу мессежийг таны URL руу дамжуулж
чадна. **Settings → Premium Number** дотор **Uses receiver**-ийг идэвхжүүлж, **Edit
receiver**-ийг бөглөнө: арга (GET эсвэл POST), бүтэн URL, мөн дөрвөн параметрийн *нэрс* —
хэрэглэгчийн дугаар, таны тусгай дугаар, мессеж, огноо. Эдгээр нэрийг та өөрөө сонгодог
тул таны endpoint болон портал хоёр тохирч байх ёстой. Хүлээн авагч нь нууц түлхүүр,
гарын үсэггүй; URL-ийг олсон хэн ч хүсэлт илгээж чадах тул сүлжээний түвшинд хязгаарлаарай.
Огнооны формат баримтжаагүй — тэмдэгт мөр хэлбэрээр хадгална. Энэ санд хүлээн авагч
ороогүй; таны ашиглаж буй HTTP framework дээр нэг жижиг route бичихэд хангалттай.

## Скайтел

Портал: `https://smsgw.skytel.mn`. Эх сурвалж: Скайтелийн PushSMS интерфейсийн заавар —
дөрвөн операторын зааврын дотроос хамгийн бүрэн нь.

**Юу хэрэгтэй вэ**

- Бүртгэлийн дугаар (`id`) болон илгээгчийн богино дугаар (`src`); хоёулаа бүртгэлийн
  захидалд бий.
- Порталын нэвтрэх эрх. Анхны нууц үгтэй ирдэг — эхний нэвтрэлтээр солиорой.
- **Change configurations → Allowed IP List** талбарт IP хаягуудаа цэгтэй таслалаар
  тусгаарлан оруулна. Хэдийг ч өөрөө нэмж, хасаж болно.

`id` нь бүртгэлийн дугаар гэж нэрлэгддэг ч нууц үг шиг ажилладаг: IP хаягтай тань хамт
бүхэл нэвтрэх мэдээлэл болдог. Лог болон эх кодын санд бүү оруулаарай.

**Тохиргоо**

```ts
skytel: { id: "…", src: "…" }   // baseUrl-ийн анхны утга: https://smsgw.skytel.mn
```

**Хүсэлт**

```
GET https://smsgw.skytel.mn/SMSGW-war/pushsms?id=<ID>&src=<SRC>&dest=91112233&text=hello
GET https://smsgw.skytel.mn/SMSGW-war/unicode?id=<ID>&src=<SRC>&dest=91112233&text=<кирилл>
```

**Цагаан толгойгоор ялгаатай хоёр endpoint.** `/pushsms` нь латин текст дамжуулна. Бусад
бүх текст `/unicode` руу явах ёстой, эс бөгөөс хэрэглэгчид эвдэрсэн тэмдэгт очно. Энэ сан
мессежийг хараад өөрөө сонгодог: цэвэр ASCII бол `/pushsms`, бусад нь `/unicode`. Танаас
юу ч шаардахгүй.

**Хариу.** HTTP 200 дотор энгийн текст.

| Хариу | Утга |
| --- | --- |
| `OK` | Хүлээн авсан. |
| `ERROR: 101 …` | Шаардлагатай параметр дутуу. |
| `ERROR: 102 …` | Илгээгчийн дугаар (`src`) буруу. |
| `ERROR: 103 …` | Хүлээн авагчийн дугаар (`dest`) буруу. |
| `ERROR: 201 …` | Параметр буруу. |
| `ERROR: 202 not authenticated` | `id` буруу **эсвэл** IP хаяг бүртгэлгүй — аль нь болохыг хариу хэлдэггүй. Эхлээд IP жагсаалтаа шалгаарай. |
| `ERROR: 203 account disabled` | Бүртгэл хаагдсан. |
| `ERROR: 206 …` | Хүлээн авагч өөр сүлжээнийх. Энэ бүртгэл зөвхөн Скайтелийн дугаар руу илгээнэ. |
| `ERROR: 207 …` | `src` нь энэ бүртгэлд бүртгэлтэй илгээгч биш. |

Кодын дугаар `error.gatewayCode`-д орно; хүснэгтийг `SKYTEL_ERRORS` нэрээр экспортолсон.

**Хязгаар.** `text` нь хамгийн ихдээ **160 тэмдэгт**. Гарц урт мессежийг хуваадаггүй. Энэ
сан ийм мессежийг хүсэлт илгээхээс өмнө буцаана (`message_too_long`).

**Хугацаа.** Зааварт сервер 20 секундын дотор хариу өгнө, 20 секундээс хэтэрвэл сүлжээний
тасралт гэж үзэх бөгөөд *илгээгдсэн төлөв тодорхойгүй* гэж бичсэн. Энэ сангийн `timeoutMs`-ийн
анхны утга эндээс гаралтай бөгөөд хугацаа хэтрэхийг алдаа гэж биш, тусдаа `timeout` кодоор
мэдээлдгийн шалтгаан ч энэ. Дахин илгээвэл хоёр дахь хувь очиж магадгүй.

**Хариу мессеж хүлээн авах.** Webhook байхгүй. Ирсэн мессежийг порталаас уншина.

## Мобиком

Эх сурвалж: бүртгэлийн захидал. **Мобикомын гарц дөрвөн операторын дотроос хамгийн бага
баримтжсан** бөгөөд энэ хэсэгт юу баталгаажаагүйг ил хэлсэн.

**Юу хэрэгтэй вэ** — бүгд бүртгэлийн захидлаас:

- Гарцын хаяг. Хост нэр биш, энгийн HTTP дээрх цэвэр IP хаяг байж болно. Энэ санд үүний
  **анхны утга байхгүй** — захидалд бичсэнийг `baseUrl` болгон дамжуулна.
- `servicename` — таны бүртгэл илгээдэг үйлчилгээний нэр.
- `username` — бүртгэлийн нэр.
- `from` — илгээгчийн богино дугаар.
- Серверийн IP хаягаа Мобикомд бүртгүүлэх. Үүнийг порталаар биш, Мобиком өөрөө хийдэг.

**Нууц үг байхгүй.** Username болон эх IP хаяг хоёр нийлээд бүхэл нэвтрэх мэдээлэл болдог
тул IP жагсаалт л цорын ганц жинхэнэ хамгаалалт. Тэгсэн ч username-ийг нууц гэж үзээрэй.

**Тохиргоо**

```ts
mobicom: {
  baseUrl: "http://<захидалд бичсэн гарцын хаяг>",
  serviceName: "…",
  username: "…",
  from: "…",
}
```

**Хүсэлт**

```
GET <baseUrl>/smsmt/mt?servicename=<SERVICE>&username=<USERNAME>&from=<FROM>&to=99112233&msg=hello
```

Хоёр цагаан толгойд нэг endpoint; кирилл текстийг UTF-8-аар percent-encode хийж илгээнэ.

**TLS байхгүй.** Username болон мессеж бүрийн агуулга шифрлэгдээгүй дамжина. Илгээж буй
мэдээлэлд тань энэ тохирохгүй бол Мобикомд тавиарай — оператор руу VPN эсвэл түрээсийн
шугам татах нь түгээмэл шийдэл — учир нь клиент талаас үүнийг засах арга байхгүй.

**Хариу.** Энгийн текст.

- `Sent` — хүлээн авсан.
- Бусад бүх хариу — татгалзсан гэж үзэж, хариуг яг байгаагаар нь буцаана.

⚠️ **Баталгаажаагүй.** `Sent` гэсэн үг Мобикомын баримт бичгээс гараагүй бөгөөд энэ санд
Мобикомын татгалзлын мессежүүдийн жагсаалт байхгүй. Тиймээс зөвхөн `Sent`-ийг хүлээн
зөвшөөрч, бусдыг таамаглахаас татгалздаг. Хэрэв `response` нь өөр үгээр амжилттай мэт
харагдах `rejected` үр дүн гарвал хариуг яг байгаагаар нь хавсаргаж issue нээнэ үү.

**Хязгаар.** Уртын хязгаар, хүлээх хугацаа баримтжаагүй. Уртыг шалгахгүй; гацсан гарц
хүсэлтийг барьж суухгүйн тулд 20 секундын хугацааг Скайтелээс авсан.

## Жи-Мобайл

Эх сурвалж: тусгай дугаар эзэмшигчдэд зориулсан Жи-Мобайлын нэг хуудас API заавар.

**Юу хэрэгтэй вэ**

- `username` болон `password`.
- `from` — таны тусгай дугаар.
- Серверийн IP хаягаа Жи-Мобайлд бүртгүүлэх. Хүсэлтээр Жи-Мобайл хийдэг.

Дөрвөн операторын дотроос жинхэнэ нууц үгтэй цорын ганц нь.

**Тохиргоо**

```ts
gmobile: { username: "…", password: "…", from: "…" }
// baseUrl-ийн анхны утга: http://sms-special.gmobile.mn
```

**Хүсэлт**

```
GET http://sms-special.gmobile.mn/cgi-bin/sendsms?username=<U>&password=<P>&from=<FROM>&to=98112233&text=hello
```

Хоёр цагаан толгойд нэг endpoint; кирилл текстийг UTF-8-аар percent-encode хийж илгээнэ.
Нэг хуудас зааварт параметрээр зөвхөн `from`, `to`, `text`-ийг жагсаасан; `username`,
`password` нь бүртгэлтэй хамт ирдэг.

**TLS байхгүй.** Нэвтрэх мэдээллийн хоёр хэсэг хоёулаа, мөн мессеж бүр шифрлэгдээгүй
дамжина. Мобикомтой адил анхааруулга хамаарна.

**Хариу.** HTTP 200 дотор энгийн текст.

| Хариу | Утга |
| --- | --- |
| `0: Accepted for delivery` | Хүлээн авсан. |
| `error1` | Параметр дутуу дамжуулсан. |
| `error2` | Тусгай (илгээгчийн) дугаар үүсээгүй. |
| `error3` | Зөвшөөрөлгүй IP хаягаас хандсан. |
| `error4` | Мессеж илгээх эрх хаагдсан. |
| `error5` | Хүлээн авагчийн дугаар буруу. |
| `error6` | 160 тэмдэгтээс урт текст илгээсэн. |

Токен нь `error.gatewayCode`-д, утга нь (англиар) `error.message`-д орно; хүснэгтийг
`GMOBILE_ERRORS` нэрээр экспортолсон.

URL-ийн зам болон хүлээн авсан хариуны мөр нь нээлттэй эхийн SMS гарц
[Kannel](https://www.kannel.org/)-ийнх. Kannel нь SMS төв рүү холболт тасарсан үед
`3: Queued for later delivery` гэж бас хариулж чаддаг. Жи-Мобайлын зааварт энэ хариу
байхгүй тул энэ сан мессеж явна гэж таамаглахын оронд `rejected` гэж мэдээлдэг. Ийм хариу
гарвал мессеж дараа нь хүргэгдэж *магадгүй* — OTP-г сохроор дахин илгээж болохгүй.

**Хязгаар.** **160 тэмдэгт**; хүсэлт илгээхээс өмнө шалгадаг (`message_too_long`) тул та
`error6`-г бодит байдал дээр хэзээ ч авах ёсгүй.

## ОНДО

ОНДО дугаарын хуваарилалттай (60, 66, 8181 блокууд) боловч энэ санд гарц нь байхгүй.
ОНДО-гийн дугаар руу илгээхэд сүлжээний хүсэлтгүйгээр `unsupported_operator` буцна.
Хэрэв та ОНДО-гийн API-г холбосон бол pull request илгээхийг урьж байна: `src/operators/`
дотор нэг файл, чиглүүлэлтийн хүснэгтэд нэг мөр л нэмнэ.

## Дугаарын хуваарилалт

Чиглүүлэлт нь Харилцаа холбооны зохицуулах хорооноос (ХХЗХ) ITU-д мэдүүлсэн Монгол Улсын
дугаарлалтын үндэсний төлөвлөгөөний үүрэн холбооны хуваарилалтыг ашигладаг (2026-01-28-ны
мэдэгдэл): <https://www.itu.int/dms_pub/itu-t/oth/02/02/T020200008E0008PDFE.pdf>

| Оператор | Хуваарилалт |
| --- | --- |
| Мобиком | 99, 95, 94, 85 · 505–509 · 555–559 |
| Юнител | 88, 89, 86, 80 · 500–504 · 550–554 |
| Скайтел | 91, 90, 96 · 690, 696, 699 |
| Жи-Мобайл | 980–981, 988–989 · 930–931 · 970–971 · 830–831 · 8700–8711 |
| ОНДО | 600–604, 6050, 606, 6070 · 660, 661, 666, 669 · 8181 |

Энэ хүснэгтийн тухай гурван зүйл:

- **Угтвар биш, муж.** `50` болон `55` нь Юнител, Мобиком хоёрын дунд яг голоороо
  хуваагдсан. Скайтелийн `69` нь тусдаа гурван зүсэм. Жи-Мобайл `980–981` болон `988–989`-ийг
  эзэмшдэг ч `982–987`-г эзэмшдэггүй. Эхний хоёр оронгоор хайвал эдгээрийг буруу тодорхойлно.
- **Буцаан татсан блокуудыг зориуд орхисон.** Операторын зохицуулагчид буцааж өгсөн блок
  нь урьд эзэмшиж байсан оператор руу чиглэхийн оронд `unallocated_number` гэж гарна.
- **Хуучирдаг.** Хуваарилалт өөрчлөгддөг. Хүснэгт сангийн дотор ирдэг тул шинэчлэлтийг
  санг шинэчилж авна. Хүчинтэй дугаар `unallocated_number` гэж буцвал одоогийн төлөвлөгөөг
  шалгаад issue нээнэ үү.

**Дугаараа хадгалан шилжихийг тооцоогүй.** Өөр оператор руу шилжсэн хэрэглэгч дугаараа, мөн
түүнтэй хамт хуваарилалтаа хэвээр хадгалдаг. Хуваарилалтаар чиглүүлэхэд мессеж орхисон
операторынх нь гарц руу очиж, татгалзсан хариу авна. Шилжсэн дугаарын нээлттэй сан байхгүй.
Жинхэнэ операторыг өөр аргаар мэдсэн бол `send()`-д `operator` дамжуулаарай.

## Нэвтрүүлэхийн өмнөх шалгах хуудас

- [ ] Хэрэгтэй оператор бүртэй гэрээ байгуулж, илгээгчийн дугаар авсан.
- [ ] Бодит орчны тогтмол гадаад IP хаягийг оператор **бүрт** бүртгүүлсэн.
- [ ] Туршилтын орчин жинхэнэ мессеж илгээдэг бол түүнийг ч мөн адил.
- [ ] Нэвтрэх мэдээллийг нууцын санд хадгалсан. Скайтелийн `id`, Мобикомын `username` нь
      нууц үг гэж нэрлэгдээгүй ч нэвтрэх мэдээлэл мөн.
- [ ] Сүлжээ **бүр** дээр өөрийн эзэмшдэг SIM рүү туршилтын мессеж илгээсэн. Юнител дээр
      амжилттай болсон нь Мобикомын тухай юу ч хэлэхгүй.
- [ ] `result` бүрийг логт бичсэн — `request`, `response` хоёрт нэвтрэх мэдээлэл аль хэдийн
      ороогүй байдаг. Нэхэмжлэхтэй маргах үед энэ нь таны баримт болно.
- [ ] Нийтэд нээлттэй бүх зүйлийн, ялангуяа OTP endpoint-ийн урд хүлээн авагч тус бүрийн
      хүлээх хугацаа болон өдрийн дээд хязгаар тавьсан. Энэ сан аль алийг нь хэрэгжүүлдэггүй.
- [ ] `timeout`-ийн талаар шийдвэр гаргасан: OTP-ийн хувьд ижил кодыг дахин илгээхээс
      *шинэ* код үүсгэх нь аюулгүй.
- [ ] Дэд бүтцээ нүүлгэхийн өмнө: шинэ IP хаягуудыг **эхлээд** дөрвөн жагсаалтад нэмсэн.
